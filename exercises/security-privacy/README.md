# Security and Privacy exercises

These are constructed, offline fixtures. Paths here start at the companion root.
Code in this process is trusted. No exercise builds an operating-system sandbox.

For exercises 1–5, repair the corresponding `security_privacy_0N.py` answer and run
`python -m pytest exercises/security-privacy/test_security_privacy_acceptance.py`.
The five supplied answers fail for different, deliberate misconceptions. The
reference answers are in `security_privacy_answers.py`; set
`SECURITY_PRIVACY_REFERENCE=1` to check them.

Exercise 5 uses `day-05.json`, generated by `security_privacy_day_05.fixture`.
Its twelve requests include one over-broad credential, a proper expiry and
reissuance, two indistinguishable order refusals, and payment-scope revocation.
Diagnose issuance and the resulting disclosure, then address the intake owner.
The generator corrupts one trusted account-to-orders grant at intake. Both
credential issuance and the real resolver read that same grant input. The faulty
row's decision, credential log and audit record come from the real tools; the
shipped resolver still rejects an over-broad credential against clean grants.

Exercise 6 starts at `security_privacy_delegate_06.py`. Run
`python -m pytest exercises/security-privacy/test_security_privacy_exercise_06.py`.
The starter fails exactly two tests: expiry and onward delegation. The reference
is `security_privacy_reference_06.py` (public). The owner authenticates a
grant; intake rereads current grants and issues a fresh credential for each run.
The delegated operation is asking for a refund on that order. Execution still
uses the agent's grant and returns money to the order's original payment.

Set `SECURITY_PRIVACY_SOLUTION` to your submission's Python path, or to the public
`security_privacy_reference_06.py`, before running the acceptance file. Only the
selected file is loaded.
